# E3 一页说明：规格先行与 AI 结对修复

题目：E3-02 购物车合并的修改时间（个人选题，非教师示例）。

| 五问 | 填写内容 |
|---|---|
| 原来的问题是什么？ | `OmsCartItemServiceImpl.add` 合并购物车时，把 `modifyDate` 设到传入的 `cartItem`（不会被持久化）上，而 `updateByPrimaryKey` 持久化的是 `existCartItem`，导致数据库里合并后条目的修改时间始终停留在旧值。 |
| 依据是什么？ | 缺陷位置 `mall-portal/.../service/impl/OmsCartItemServiceImpl.java` 第 50 行（`cartItem.setModifyDate`）与第 52 行（`updateByPrimaryKey(existCartItem)`）对象不一致；规格「修改时间应刷新到被保存的条目」对应业务不变量：合并是更新已有行，时间戳必须落在已保存的那一行上。 |
| 我做了什么？ | 写可判定规格（输入=同会员/同商品/SKU 的已存在条目；期望=数量累加且 modifyDate 落在调用时间窗内；不改=数量公式、插入分支、公开接口）。写失败测试 `CartMergeModifyDateTest`（`mergeRefreshesSavedModifyDate` 为红灯，`insertKeepsCreateDateAndMemberSource` 为回归），先跑出红灯，再做一行最小修复，再跑同组测试绿灯。 |
| 为什么这样做？ | 遵循「先红后绿」：红灯必须来自业务断言（`saved modifyDate=1000`），不是编译或环境错误。最小修复只改第 50 行，换取「改动最小、回归面最小」的代价：不改数量累加、不重写合并算法。 |
| 怎样证明？ | `SDC/compare.sh E3-20244350127`：改前 `fail`（预期 fail）、改后 `pass`，结论「符合」（`evidence/compare.txt`）；只提交测试时改后仍 `fail`、结论「不符合」证明红灯先行（`evidence/compare-red.txt`）；覆盖率 `OmsCartItemServiceImpl.add` 行 12/12、分支 2/2（`evidence/coverage.txt`）。未验证：真实数据库/控制器端到端路径。 |

页尾：

- **AI 使用**：Claude（Claude Code）全程执行定位、写规格、写测试、一行修复、跑对照与覆盖率；人工须逐项核对 diff 为最小修复、复述规格与红灯含义。详见 `AI使用记录.md`。
- **证据来源**：本人（含 AI 结对）运行 `SDC/compare.sh` 与 JaCoCo 命令；改前/改后输出均为本机实际运行结果，非历史回放。
