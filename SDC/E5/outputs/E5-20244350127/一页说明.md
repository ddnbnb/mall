# 一页说明 —— E5-03 收货地址邮政编码规则（变更影响分析）

## 原来的问题是什么？

收货地址的 `postCode` 目前由 add/update 原样透传给 Mapper，不做任何校验。拟新增规则：邮编可空，`strip()` 去两端空白后非空必须是**六位 ASCII 数字**，新增 null 原样保留、更新未传不覆盖旧值、纯空白写成 `""`，只约束新写入不迁移旧行。本实验只做影响分析并锁定现状，**不实现规则**（实现留给 E6）。

## 依据是什么？

入口 → 接口 → 服务 → 存储/调用方，逐层行号：

```
POST /member/address/add           UmsMemberReceiveAddressController.add      28
POST /member/address/update/{id}   UmsMemberReceiveAddressController.update   50
  UmsMemberReceiveAddressServiceImpl.add     26-30  setMemberId(28) → insert(29)
  UmsMemberReceiveAddressServiceImpl.update  41-60  setId(null)(42)；defaultStatus==1 先清旧默认(57)再 updateByExampleSelective(59)
    UmsMemberReceiveAddressMapper.xml   insert 108-119 始终写 post_code；updateByExampleSelective 209-211 仅 postCode!=null 时写
      ums_member_receive_address.post_code varchar(100)  mall.sql:2839
读方：OmsPortalOrderServiceImpl 200→203  getItem 后把已存邮编抄入订单 receiverPostCode
```

服务不读不校验 `postCode`；字段 `postCode` 是 `String`（模型 20 行）。

## 为什么这样做？

**落点选服务层**：add/update 的共同入口，一处私有方法集中判断，避免第二套规则。**一项代价**：地址写入方法新增校验职责（可接受，规则简单）。

**风险（按触发顺序，最可能出错的是①）**：
1. **校验晚于清旧默认**：`update` 在 defaultStatus==1 时先清旧默认(57)再主更新(59)，校验放错位置会先改掉默认地址再拒绝。
2. null 与空白混同 → 未传字段被清空旧邮编。
3. `Integer.parseInt`/宽泛正则丢前导零或接受全角数字。
4. 订单仍抄旧行原文(200-203) —— 读旧数据，预期，非漏洞。
