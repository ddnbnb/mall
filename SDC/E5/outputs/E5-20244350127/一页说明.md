## 一、讲清楚：需求、边界与改动/不改动清单

**需求与不改边界**：教学场景限定国内地址。邮编可空；`strip()` 去掉两端空白后，非空值必须是**六位 ASCII 数字**。新增时 null 原样保留；更新时未传/null 不覆盖旧值；纯空白写成 `""`。只约束新写入，不迁移旧行；格式合法≠地址真实，不扩展行政区/街道校验。**不改**：服务接口签名、HTTP 返回、Mapper XML、表结构、生成代码。

**现状与调用链**（入口 → 接口 → 服务 → 存储/调用方）：

```
POST /member/address/add           UmsMemberReceiveAddressController.add      controller:28
POST /member/address/update/{id}   UmsMemberReceiveAddressController.update   controller:50
  UmsMemberReceiveAddressServiceImpl.add     26-30  setMemberId(28) → addressMapper.insert(29)
  UmsMemberReceiveAddressServiceImpl.update  41-60  setId(null)(42)；defaultStatus==1 先清旧默认(57)，再 updateByExampleSelective(59)
    UmsMemberReceiveAddressMapper.xml   insert 108-119 始终写 post_code；updateByExampleSelective 209-211 仅 postCode!=null 时写
      ums_member_receive_address.post_code varchar(100)  mall.sql:2839
读方：OmsPortalOrderServiceImpl 200→203  getItem 后把已存邮编抄入订单 receiverPostCode
```

服务不读不校验 `postCode`，原样交给 Mapper；字段 `UmsMemberReceiveAddress.postCode` 是 `String`（模型 20 行）。

**改动与不改动清单**：

| 文件:行号 | 改/不改 | 理由 |
|---|---|---|
| `UmsMemberReceiveAddressServiceImpl` add(26-30) / update(41-60) | **改** | 两个写入入口的唯一交点；调用同一私有规范化方法，且在**任何 Mapper 写入之前**执行 |
| `UmsMemberReceiveAddressController` add(28) / update(50) | 不改 | 只转交请求体，不该有第二套规则 |
| 生成模型 `UmsMemberReceiveAddress`（MBG） | 不改 | MBG 重新生成会覆盖；模型分不清“新增保留 null”与“更新未传” |
| `UmsMemberReceiveAddressMapper.xml` 与表结构 | 不改 | 已是 VARCHAR；selective 更新的 null 跳过(209-211)正是“未传不覆盖”所需 |
| `OmsPortalOrderServiceImpl`(200-203) | 不改 | 只读地址；旧行读出什么就抄什么 |

## 二、有依据：落点、被排除方案与风险（触发顺序）

**落点**：服务实现层（两个写入入口交点，一处私有方法集中规范化），不是控制器、不是生成模型。

**被排除的方案**（每条附具体理由）：
- × **改生成模型**：MBG 重新生成会覆盖手写 setter，且模型层不知道当前是新增还是更新，无法区分 null 语义。
- × **改成整数列**：`001234` 会丢失前导零（当前 `String`/`varchar(100)` 才能原样保留）。
- × **只改控制器**：服务才是 add/update 的共同入口，控制器之外的其他调用方会绕过校验。

**兼容性 / 数据 / 失败风险（按触发顺序）**：
1. **校验晚于清旧默认**（最可能出问题）：`update` 在 defaultStatus==1 时先执行清旧默认（57 行）再做主更新（59 行）。若把校验放在清默认之后，非法邮编会**先把当前会员的默认地址改掉再拒绝**。→ 校验必须落在 49 行分支之前。
2. **null 与空白混同**：更新未传字段若被误当空白清空，会覆盖旧邮编。
3. **数值转换丢前导零 / 接受全角**：`Integer.parseInt` 或宽泛正则会把 `001234` 变 `1234`、接受 `００１２３４`。
4. **订单仍抄旧行原文**（200-203）：这是读旧数据，不是校验漏洞，不迁移时属预期。
